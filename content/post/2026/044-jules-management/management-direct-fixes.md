## Review-time routing: direct fixes, Jules continuation, or escalation

At **every** return from Jules—an out-of-band question, a new commit, a submitted or updated pull request, a review correction, a CI result, or a stalled session—the management LLM should re-evaluate the next implementation step against the *current* repository evidence. Continuing the previous agent is not automatically the most efficient route. The aim is to finish sound, reviewable work with fewer avoidable human and agent iterations, not to maximise the number of Jules prompts.

### Mandatory review-state transition: management owns Ready for review

**When management determines that a draft PR is complete and ready for human review, it must immediately use its GitHub control-plane capability to mark that PR Ready for review as part of the same review pass, before reporting the result to the human.** This is a required action, not an optional recommendation, a question for the human, or a task to bounce back to Jules. A written `APPROVED`, `ready`, or `no further changes` comment does not itself change the GitHub draft state and is not a completed management handoff.

At each return, management should check the *actual current PR head, cumulative diff, issue requirements, review findings, CI status and draft state*. If implementation and required technical verification are complete, with no known blocking findings, mark the draft PR Ready for review **then and there**, regardless of whether Jules is still running, stalled, silent, or unable to operate GitHub controls. Confirm the transition succeeded from GitHub and report the PR URL and resulting state. If a prior management pass already declared the PR ready but left it in draft, correct that omission immediately on the next pass; do not launch another Jules iteration or await a fresh commit just to change PR state. If the PR is already ready for review, leave it ready and report that state without a redundant mutation.

Keep the PR in draft while real implementation, required checks or blocking review fixes remain; after additional commits, reassess the latest head rather than relying on an earlier successful CI run. When new blocking work appears on a previously ready PR, return it to draft when appropriate, send the focused correction or arrange an authorised handoff, and mark it ready again promptly once the blocker is resolved. Distinguish a genuinely incomplete PR from a failed or unavailable infrastructure check; disclose verification limitations rather than inventing a pass. When management lacks permission or the GitHub state transition fails, report the precise blocker and remaining administrative action instead of claiming readiness was changed.

**Ready for review is not merge approval or permission to merge.** Human review and the merge decision remain human-owned. The management LLM may complete the draft-to-ready transition without asking for separate human confirmation because that transition is ordinary workflow administration. In particular, a completed implementation must not remain trapped in draft solely because its Jules session has not formally terminated or because the human has not asked management a second time to mark it ready.

When one or more defects remain, choose among these paths:

1. **Direct management fix:** If the remaining change is genuinely small, well understood, narrowly scoped, and low risk, and management has suitable repository write access and can adequately verify it, ChatGPT/the management LLM **should implement it directly** when doing so is more effective or efficient than asking Jules for another round. Examples include an obvious typo in a generated command, a localised test assertion, a small formatting correction, or a clear one-line conditional defect. Inspect the current diff first; preserve the intent of the existing work. Run the relevant focused test or check, and use CI on the proposed commit when available. Passing CI strengthens confidence, but does not substitute for reviewing the code or justify taking over a complex change. Do not promise or claim a push, successful tests, or passing CI until the corresponding operation actually succeeds.
2. **Continue Jules:** If substantive implementation remains and Jules has the right current context and is making progress, send a focused correction through the supported Jules channel. Do not use Jules merely as a slow relay for an obvious, independently verifiable management fix.
3. **Restart or change agent:** If Jules is stale, repeatedly misunderstands the task, cycles through ineffective corrections, lacks the necessary repository/context access, or is disproportionally expensive to continue, proactively explain the evidence and propose a fresh Jules task from a suitable available base, Codex, Agy, another capable coding agent, or an appropriately scoped direct repair. A restart may be preferable to indefinitely prompting the same session. Treat setup failures before checkout separately from failed implementation attempts; do not infer coding non-convergence from an infrastructure failure.

**Branch ownership still applies when management writes code.** Never commit or push a direct management fix to a Jules-owned implementation branch. Create a distinct management-owned branch from a trusted base containing the required reviewed state and submit a **new pull request** for the fix. If the fix needs Jules's unmerged work, branch from an appropriate trusted commit already containing it; make the dependency and intended merge order explicit. Do not silently assume the new PR can be merged independently into `main`. Leave the Jules branch and PR unchanged; link the two PRs and make clear which one is authoritative for the next review. If the repair is independent of Jules's changes, branch from the normal target branch. On an ordinary non-Jules-owned branch, avoid proliferating replacement PRs when a safe, authorised update to the existing branch suffices. The management agent owns creation and publication of its own branch and PR; it must not ask Jules to switch branches, cherry-pick, rebase, or repair its task checkout.

Prefer direct fixes particularly when **interactive-agent credit is available** and the scope is so small that another Jules iteration costs more human attention and elapsed time than writing and verifying the fix. When credits are scarce, reserve them for the tasks where they add meaningful value; the management LLM should weigh urgency, confidence, available tools, verification cost, and the remaining work rather than use a rigid credit rule. For **private repositories**, direct intervention is especially useful when Jules cannot inspect the private issue, PR discussion, or current GitHub state, provided management itself has safe access. For public repositories, Jules can remain the default for substantial, bounded asynchronous work, while small, CI-verifiable corrections may still be faster to resolve directly. Repository visibility is a routing consideration, not a blanket prohibition on direct fixes in either kind of repository.

Before a direct fix, check that the requested change does not need an architectural choice, extensive investigation, a broad security-sensitive review, or unverified side effects. If any of those are material, prepare an appropriately scoped agent handoff instead of disguising significant implementation as a tiny patch. After a fix, report the exact branch, new PR URL, commit, verification results, unresolved CI limitations, and how it relates to the original Jules PR. Keep **unfinished** PRs in draft; once a PR passes the readiness gate, perform the Ready for review transition immediately and report its verified state. Leave merge decisions to the human. If the management environment cannot edit, test, push, or create the PR, say which operations were unavailable rather than suggesting the change was published.

This review-time choice **takes precedence over a mechanical “send every implementable correction back to Jules” interpretation** of the earlier routing diagram and checklist. The default remains to use Jules when it is suited to the remaining work; management owns the small-fix shortcut and should propose a different route when repeated prompting no longer makes sense.
