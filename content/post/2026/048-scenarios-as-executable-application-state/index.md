There is a recurring problem in application development that tends to acquire a collection of unrelated solutions.

Tests need data. Developers need a populated application to work against. Demonstrations need a recognisable set of users and content. Screenshots need a known visual state. Bug reports need a reproducible situation. Continuous integration sometimes needs to run the application against something more interesting than an empty database. An LLM working on a user interface needs to be able to create exactly the state it is trying to inspect.

The usual answers are fixtures, database dumps, ad-hoc seed scripts, migration-time inserts, test factories, mocks, API scripts, and hand-written JSON. Because each solves one symptom, they often drift apart. The test factory produces state the developer cannot see in the browser. The database dump rots because it references an old schema. The API script is too slow to run for every unit test.

There is a unified alternative: the scenario.

## What is a Scenario?

A scenario describes application and domain intent rather than physical database state.

It is a portable, deterministic list of domain operations—such as "create a user," "start a topic," or "grant a permission." When you run a scenario, the application itself decides how that intent is mapped to the current storage schema.

This architectural distinction is critical. A scenario is not a SQL fixture, nor is it a recording of HTTP traffic.

* **Direct SQL is too low-level.** A database dump or SQL fixture encodes exactly how tables looked at one moment in time. When the schema changes, the dump breaks. When internal identity sequences advance, foreign keys must be manually reconciled.
* **HTTP replay is too high-level.** Replaying a series of HTTP requests requires booting a web server, dealing with authentication tokens, parsing JSON bodies, and handling network timeouts. It is a slow, brittle way to construct state.

Instead, scenarios sit in the middle. The typical request path looks like this:

`HTTP -> transport/auth/request handling -> application/domain operation -> repository/storage`

A scenario bypasses the transport layer completely and calls the identical domain operations:

`scenario operation -> application/domain operation -> repository/storage`

By reusing the real application functions for user creation, permission processing, and content generation, the scenario remains resilient to schema changes while executing orders of magnitude faster than a network script.

## Core Properties of a Scenario

To make a scenario portable and deterministic, it must avoid the brittleness of traditional fixtures.

### Symbolic References

Hard-coded database IDs are the enemy of maintainable state. If a scenario hard-codes `user_id = 42`, it will inevitably collide with another scenario or break when the sequence starts at a different number.

Instead, scenarios use **symbolic references** (e.g., `alice`, `staff-room`). When an entity is created, it is bound to a symbol. Later operations reference that symbol, and the scenario runner automatically resolves it to the underlying integer or UUID generated by the database. These references can and should be typed to catch errors early (e.g., trying to add a "topic" to a "user" reference instead of a "forum" reference).

### Deterministic Clocks

If an operation creates a record with "now" as the timestamp, verifying the output becomes difficult. The result will change every time the scenario runs.

Scenarios explicitly specify timestamps for their operations. The runner injects a deterministic clock into the application domain context, ensuring that entities are created at exactly the time specified in the file.

### Format Versioning and Preflight Validation

A portable scenario format must be versioned (e.g., `application-scenario/v1`). Before any state is mutated, the runner performs a preflight validation pass. It verifies that the format version is supported, all required fields are present, references are correctly typed and resolved, and any attached assets (like images) actually exist.

### Atomicity

Where the target storage permits, applying a scenario should be wrapped in a transaction. If an operation fails halfway through, the database rolls back, leaving no corrupted partial state behind.

## Adapting Scenarios to Different Domains

Not every application requires a sequential journal of operations. The scenario pattern adapts to the domain.

* **Simple Domains:** If the application manages a flat list of bookmarks with tags, a scenario might just be a declarative list of URLs and their associated metadata. The "operations" are simply upserts. The minimum domain vocabulary needed is preferable to unnecessary complexity.
* **Complex Graphs:** If the domain involves deeply nested forums, topics, and threaded replies, the scenario format might look more like an event journal, capturing the chronological interactions between users.
* **Native Formats:** If you are building an email client or server, a directory of real RFC message files (`.eml` or mbox) with a small manifest might be a much better scenario representation than inventing a custom text format. Standardise the scenario *contract and lifecycle*, not necessarily the syntax. If a native representation is better supported by the code, use it.

## Embedded vs. External Scenarios

Scenarios should be runnable in two ways: embedded and external.

A compiled binary can bundle a small catalog of versioned, built-in scenarios using language-appropriate embedding (e.g., `go:embed`). These provide instant, guaranteed-to-work examples for developers and demonstrations. Crucially, these embedded examples **must run in CI**. If an application change breaks a scenario, the build should fail immediately rather than letting the example rot.

Simultaneously, the CLI or test APIs should accept user-provided files or directories, allowing developers to craft ad-hoc scenarios for reproducing bugs or testing edge cases.

A generic CLI implementation typically provides commands like:
* `scenario list` (show embedded scenarios)
* `scenario show` (print a scenario's contents)
* `scenario validate` (run preflight checks)
* `scenario apply` (execute against a database)
* `scenario serve` (boot a disposable server populated by the scenario)

## Disposable and Persistent Targets

Applying scenarios to disposable, in-memory databases is straightforward. An in-memory repository or temporary SQLite file is instantiated, the scenario is applied, and the application is served. When the process dies, the state vanishes. This is ideal for tests and safe local development.

Applying scenarios to persistent, long-lived databases requires safety rails. The runner should require explicit target selection, perform dry-run preflight checks, and enforce policies like "only apply to empty databases" or robust idempotency semantics to prevent accidental corruption of production data.

## Migrations vs. Scenarios

It is important to distinguish scenarios from database migrations and mandatory bootstrap state.

* **Migrations** handle historical persisted state. They evolve an old database schema to a new one.
* **Bootstrap State** is the core policy, roles, and reference data required for *every* valid installation to function.
* **Scenarios** represent optional examples, demonstrations, feature states, and test situations.

State required for every valid installation belongs in migrations or mandatory bootstrap. Optional situations belong in scenarios. However, both should reuse the same common application domain provisioning functions to avoid duplicating policy logic. A scenario replayed by the current application tests the application's ability to *construct* state; an old database snapshot tests *migration*. Neither replaces the other.

## LLM-Assisted Development

This architecture is uniquely valuable in an LLM-assisted development environment.

Rather than relying on vague claims about AI, consider the concrete mechanical benefits: an LLM can be instructed to create a scenario file representing a specific edge case. It can run the scenario, render a view against it, verify the change, and hand exactly the same reproducible, named state file to CI or a human reviewer.

By exposing scenario operation metadata and examples as a repository agent skill (e.g., in an `AGENTS.md` file), coding agents gain a deterministic, reliable way to instantiate complex application states without guessing database schemas or writing brittle SQL.

## When It Fails: Anti-Patterns

The scenario pattern is paying its way if you see shared operations, multiple scenarios reused across different consumers (tests, demonstrations, CI), reduced setup duplication, and a simpler debugging loop.

It has failed if you observe these anti-patterns:
* **Schema-shaped scenarios:** The format mirrors the SQL tables rather than domain actions.
* **Direct SQL:** Normal domain actions bypass the application layer and write raw SQL.
* **HTTP replay:** Complex network scripts are masquerading as state construction.
* **Generated IDs in files:** Hard-coding integers or UUIDs instead of using symbolic references.
* **Uncontrolled time:** Relying on `time.Now()` during execution.
* **Unvalidated partial applies:** Executing operations without preflight validation, leading to half-broken states.
* **Rotting examples:** Scenarios that never run in CI.

By treating scenarios as executable application intent rather than static data, you build a foundation that serves tests, developers, continuous integration, and coding agents with equal reliability.

## Example: A Generic Scenario Format

Consider a generic `TXTAR` based scenario file for a blog system:

```text
-- scenario.meta --
Format: blog-scenario/v1
Name: example-blog

-- 010-author.event --
Op: user.create
Ref: author-bob
Username: bob
Role: author
At: 2026-09-01T10:00:00Z

-- 020-post.event --
Op: blog.post
Ref: first-post
Author: author-bob
Title: Hello World
At: 2026-09-01T10:05:00Z

This is the content of the first post.
```

This intent is executed by mapping operations in a registry to real domain functions:

```go
type OperationRegistry map[string]func(ctx context.Context, runner *Runner, evt Event) error

func RegisterOperations() OperationRegistry {
	return OperationRegistry{
		"user.create": func(ctx context.Context, runner *Runner, evt Event) error {
			// Preflight check
			username := evt.Props["Username"]

			// Reuse actual application creation logic
			user, err := app.CreateUser(ctx, username, evt.Props["Role"], evt.At)
			if err != nil {
				return err
			}

			// Bind the generated ID to the symbol for future events
			runner.BindRef("user", evt.Ref, user.ID)
			return nil
		},
		"blog.post": func(ctx context.Context, runner *Runner, evt Event) error {
			// Resolve symbolic author ID
			authorID := runner.ResolveRef("user", evt.Props["Author"])

			post, err := app.CreatePost(ctx, authorID, evt.Props["Title"], evt.Body, evt.At)
			if err != nil {
				return err
			}

			runner.BindRef("post", evt.Ref, post.ID)
			return nil
		},
	}
}
```
