Building command-line applications in Go often leads you down the path of needing nested subcommands. While the standard library's `flag` package is great for simple tools, it can become unwieldy when you want a rich structure like `git commit` or `docker run`. This is where utilizing a dedicated library for generating a subcommand infrastructure shines.

In this post, we'll look at how to convert or set up an application to use [go-subcommand](https://github.com/arran4/go-subcommand) (or a similar pattern) to cleanly separate command logic, and then we'll layer in a fascinating workflow trick: teaching an LLM agent to automatically generate `bug.md`, `gap.md`, and `featurerequest.md` files while working on your CLI.

## Structuring Your App with go-subcommand

When using a subcommand router, the goal is to shift from a massive `main()` function parsing flags to isolated command handlers.

One of the huge benefits is that you don't even need a `main()` function anymore. `go-subcommand` can generate the whole `/cmd` directory for you, and it can even set up your `goreleaser` file and more. This eliminates a lot of boilerplate right from the start.

### 1. The Power of Auto-Generation

By defining your command structure and letting `go-subcommand` do the heavy lifting, you get an instantly runnable application. Each subcommand becomes its own isolated domain. For example, if you are building a real-world infrastructure tool:

```go
package mycli

import (
    "context"
    "fmt"
)

//go:generate go run github.com/arran4/go-subcommand/cmd/go-subcommand generate

// Create handles the "create" subcommand
func Create(ctx context.Context, args []string) error {
    fmt.Println("Creating infrastructure... (example: provisioning an S3 bucket)")
    return nil
}
```

This modularity means that your `create` command doesn't tangle with your `delete` command's flags.

By adhering to this structure, extending the app with new features is as simple as dropping in a new command registration.

## The LLM Feedback Loop: bug.md, gap.md, and featurerequest.md

Now for the twist. As we increasingly use LLM agents to write code or scaffolding (like generating new subcommands), we run into a problem: what happens when the LLM gets stuck, finds a missing dependency, or has a brilliant idea?

Often, they hallucinate a fix or silently fail.

Instead, you can explicitly instruct your LLM system to use specific Markdown files to communicate state and intentions back to you. When setting up your prompt template or agent instructions for the CLI project, include the following directives:

> "If you encounter an issue that prevents you from completing a task, do not hallucinate a fix. Instead, generate or append to a file named `bug.md` describing the error."

> "If you realize you lack context, a prerequisite is missing, or an API is incomplete, write the details into `gap.md`."

> "If you identify a potential improvement or a new subcommand that would be beneficial but is outside the current scope, document it in `featurerequest.md`."

### Why This Works

1.  **State Management:** It externalizes the agent's internal state. You don't have to parse a chat transcript to figure out why a build failed; it's summarized in `bug.md`.
2.  **Safe Failure:** It gives the agent a "safe path" when it hits a wall. Instead of breaking your `main.go`, it gracefully logs the missing piece in `gap.md`.
3.  **Continuous Improvement:** The `featurerequest.md` file becomes a backlog generated by an entity that is actively analyzing your codebase's structure.

By combining the clean, modular architecture of a subcommand infrastructure with explicit LLM communication channels, you create a robust environment for both human and AI developers to collaborate effectively.
